# 数据管理模块数据库设计方案（MySQL）

> 说明：本文件为**方案文档**（表结构 + 字段说明），不含可执行 SQL。
> 范围：仅数据管理模块。轨迹记录表、用户资料表由其他模块维护，本模块只引用其 ID。
> 背景：**企业园区**场景。所有字段名后括号内为中文名；数据类型使用 MySQL 类型并给出中文名与长度。

---

## 1. 设计原则

| 原则 | 说明 |
|------|------|
| **第三范式（3NF）** | 类型、状态、严重程度、人员外形等拆成独立维度表，事实表不冗余名称/描述，消除传递依赖。 |
| **星型结构** | 以异常行为记录为核心事实表，周围环绕行为类型、匿名人员、严重程度、状态等维度表，便于统计查询。 |
| **不建外部表** | 轨迹记录表、用户资料表不在本模块建，只保留 `track_id`（轨迹ID）、`user_id`（用户ID）形式的外键引用。 |
| **ID 与编码不重复** | 每一类实体只保留一个主键 ID（自增或固定枚举）；维度表只存 ID + 中文名称，不再单独建编码列；业务分类字段（角色、模块、操作类型等）保留编码，但无对应 ID 重复。 |
| **字段命名** | 主键/外键命名 `{表名单数}_{主键名}`，如 `behavior_type_id`（异常行为类型ID）、`person_id`（匿名人员ID）、`track_id`（轨迹ID）。 |

## 2. MySQL 数据类型中文对照

| MySQL 类型 | 中文名 | 长度写法 | 适用范围 |
|------------|--------|----------|----------|
| BIGINT UNSIGNED | 大整数（无符号） | 8 字节 | 主键、外键（自增） |
| INT | 整数 | 4 字节 | 耗时、数量等 |

| TEXT | 长文本 | - | 描述、详情 |
| JSON | JSON 格式文本 | - | 数组、键值对结构 |

## 3. ID 设计依据与编码规则（重点）

### 3.1 三条 ID 生成规则

| 类型 | 生成方式 | 适用字段 |
|------|----------|----------|
| **① 模块内实体主键（自增型）** | `BIGINT UNSIGNED AUTO_INCREMENT`，从 1 顺序递增，插入时由数据库自动生成，不人工干预 | `behavior_type_id`、`person_id`、`behavior_id`、`alert_id`、`work_order_id`、`log_id`、`backup_id` |
| **② 枚举型维度主键（固定值）** | `TINYINT UNSIGNED`，取值为业务固定枚举，由初始化脚本预置，不自动增长，用于状态/等级流转 | `severity_level_id`（1高/2中/3低）、`alert_status_id`（1~6）、`work_order_status_id`（1~4） |
| **③ 跨模块引用 ID（外部生成）** | 由对应模块生成，本模块只存储引用，不生成、不维护 | `track_id`（轨迹模块）、`camera_id`（设备模块）、`operator_id`/`assigned_to`/`confirmed_by`/`matched_user_id`（用户管理模块） |

### 3.2 编码规则（保留的业务编码）

除主键 ID 外，本模块保留以下业务编码字段（编码与 ID 各有用途，互不冲突）：

| 字段 | 表 | 编码规则 | 示例 |
|------|----|----------|------|
| `work_order_no`（工单编号） | fa_work_order | WO + 年月日(8位) + 4位流水，当天到 9999 后回 0001 | WO202507280001 |

> 其余维度表（异常行为类型、严重程度、预警状态、工单状态、匿名人员）因数据量小、值固定，直接用 ID 关联即可，不再单独保留编码字段。

### 3.3 设计说明

- **`person_id`（匿名人员ID）**：系统识别不出人脸，先建"匿名异常人员"档案（用外形描述），有了 `person_id` 后**轨迹模块据此 ID 建轨迹**。属于规则①自增主键。
- **`matched_user_id`（关联用户ID）+ `match_confidence`（AI匹配置信度）**：AI 尝试把匿名人员匹配到用户管理模块里的已知用户，给出匹配概率；概率高时关联真实用户，概率低则仍是匿名。两者属于规则③引用。
- **状态/严重程度用固定枚举主键（规则②）**：值固定、数量少、不增长，外键直接引用数字，查询快、易维护。
- **`track_id`（轨迹ID）**：直接引用轨迹模块，本模块不生成（规则③）。

## 4. 编码字段命名规范

> 行为种类（10 种）、角色（7 种）本次不预置具体清单，只给出**编码规则**；具体值由数据初始化时按此规则录入，以用户管理模块字典为准。

| 字段 | 编码规则 | 参考示例 |
|------|----------|----------------------------|
| 行为类型名称 `type_name` | 表内不单独存编码；若外部系统需要类型编码，规则为**大写英文+下划线**，≤32 字符，见名知意 | FALL_DOWN（跌倒）、FIGHT（打架）、INTRUSION（闯入）、GATHER（聚集） |
| 模块编码 `module_code` | 大写英文+下划线 | ABNORMAL_BEHAVIOR（异常行为）/ BACKUP_RESTORE（备份恢复）/ USER_PROFILE（用户资料） |
| 操作类型 `operation_type` | 大写英文 | QUERY（查询）/ EXPORT（导出）/ BACKUP（备份）/ RESTORE（恢复）/ UPDATE（更新）/ DELETE（删除） |
| 通知方式 `notify_method` | 大写英文，多值用逗号分隔 | POPUP（弹窗）/ SOUND_LIGHT（声光）/ PUSH（推送） |
| 备份类型 `backup_type` | 大写英文 | FULL（全量）/ INCREMENTAL（增量）/ TABLE（按表） |
| 备份状态 `backup_status` | 大写英文 | RUNNING（进行中）/ SUCCESS（成功）/ FAILED（失败） |
| 文件格式 `file_format` | 大写英文 | SQL / CSV / PARQUET |

> 注：本期**不新增备份记录表**，backup 相关编码仅作为预留规则；备份与恢复页面以前端静态占位实现，`fa_operation_log` 中的 BACKUP_RESTORE 日志仍正常记录。
